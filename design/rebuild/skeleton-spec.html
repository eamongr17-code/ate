Ate Skeleton Spec

The composition root, navigation, chrome and component set the rebuilt app stands on. Built once, before any flow, knowing all 35 screens.

The in-place rule

The app builds and ships on every merge. The skeleton PR swaps the shell and chrome under the existing screens. Each flow PR afterwards replaces one flow's screens and deletes the old ones in the same PR. Nothing is left half-migrated, and nothing custom coexists with native chrome.

0. Components first

Eamon, 3 Oct

"Ensure you are building things in a logical and atomic way." The flows were designed separately and the mockups already disagree in small ways about how the same element looks. That must not reach the build.

  • One kit, built and checked once, before any screen. Order: tokens, then atoms, then composites, then screens. A screen is only an arrangement of kit components plus data.
  • Atoms: score token, diet chip, photo thumbnail and letter tile (one component, one size and radius per list), avatar, save bookmark, glass disc, ink pill, key (composer).
  • Composites: dish row, entry slip, shelf card, hero card, ranked row, receipt, torn edge, photo cluster, empty state, skeleton, filter chip row, sheet scaffold (close left, primary right), root header (title and glass group on one row), actions sheet.
  • No local styling in a screen. No colour, font, radius, shadow or spacing literal outside App/DesignSystem/; SwiftLint enforces it. If a screen needs a look the kit lacks, the kit gains a component or a variant, reviewed once.
  • A component gallery (Debug build only) shows every atom and composite in every state, light and dark. It is checked on a phone against the contract before the first flow starts, and it is where Eamon judges the kit.
  • Where mockups disagree, the contract wins and the mockup is treated as wrong. The mockups show layout and content; the kit defines what each element looks like.
  • The same action is the same component everywhere: one Save, one actions sheet, one filter sheet scaffold, one empty state.

1. Composition root

AteApp
 └─ AteServices        (keep as is: API client, per-domain services, outbox, analytics)
     └─ AppModel       (new, @Observable: session, handle, outbox drain, link inbox)
         └─ TabShell   (new: native TabView, four TabRouters, composer presentation)
             ├─ JournalRouter / FeedRouter / SearchRouter / YouRouter
             └─ Composer (sheet, owned by the shell)
  • AppModel owns what the whole app shares: session state, the sign-in gate, the owed handle, the outbox, incoming entry links. Nothing else.
  • TabRouter is one small @Observable per tab: its [Route] path, its stores, scroll-to-top. The current 20 stores held by one view move into the four routers; a tab's stores are created when the tab is first shown.
  • The existing Route enum stays. navigationDestination(for: Route.self) is declared once, in TabShell.
  • Debug launch routes, preview data and the staging sign-in move into one DebugLaunch applied at AteApp. No #if DEBUG inside any screen (60 files carry one today).
  • One LocationService on AteServices. Only the place sheet calls it. The Feed and Search never ask.

2. Navigation and chrome, all native

  • Tab bar: SwiftUI TabView with the iOS 26 Liquid Glass bar, tabBarMinimizeBehavior(.onScrollDown). Four tabs: Journal, Feed, Search, You, Lucide icons via the existing AteIcon. Tinted with the brand's ink and coral through the tokens.
  • The + button is a tab (Eamon, 3 Oct): it takes the bar's detached trailing slot, the one iOS 26 gives a search-role tab, so it reads as its own glass circle while staying the system bar. Tapping it presents the composer sheet and never changes the selected tab. Tinted coral through the tokens.
  • Pushed pages: native navigation bar, native back, controls as ToolbarItems (glass for free). Titles via navigationTitle with toolbarTitleDisplayMode(.inline); the Journal and You roots use the large-title style with the wordmark as a toolbar item.
  • Scrolled headers: the system scroll-edge effect replaces the frost and the compact header. Filter chips sit in a safeAreaInset(edge: .top) under the bar.
  • Sheets: .sheet with presentationDetents and the system grabber; close is a glass disc top left, the primary action a glass disc top right, on every sheet. The composer is a sheet too (Eamon, 3 Oct).
  • Swipe back and the photo viewer: system gestures and system presentation only.
